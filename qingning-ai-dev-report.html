青柠国际项目：AI 辅助全流程开发提效汇报

文档性质：公司内部汇报材料 项目名称：lime-server（青柠国际后端服务） 汇报主题：使用 AI 全流程参与需求、设计、编码、测试的提效成果 受众：管理层 + 技术骨干

一、核心结论（一分钟速览）

青柠国际后端项目（lime-server）从零开始，由 AI 深度参与需求分析、技术方案设计、数据库设计、接口开发、代码实现、测试验证全链路开发，产出了一个包含完整工程规范、标准文档、自动化测试和生产级代码的后端系统。

三个关键成果：

成果 说明
AI 全链路参与 从 PRD 到代码到测试，AI 不是只写代码，而是参与了完整交付流程
工程规范沉淀 形成了一套可复用的"AI 协作规范体系"，新项目可直接复用，不必重新摸索
交付质量可控 通过规则约束、标准文档、自动化测试三层把关，AI 产出"快而可控"而非"快而乱"

一句话总结：AI 相当于一个能力很强的新人——给他配齐操作手册和质检表，产出又快又稳；没有手册和质检表，产出容易快而乱。本项目的核心价值，就是把这套"操作手册 + 质检表"建起来了。

三、行业背景：Agent Harness 是什么

3.0 从项目实践到行业概念

在这个项目中，我们建立了一套让 AI 能够规范、可控、可复现地参与开发的工程体系——包括自动触发的编码规则、标准化的文档模板、可运行的测试验证等。项目做完后学习智能体工程才发现，这套做法在行业中有一个对应的概念叫 Agent Harness。

需要澄清的是：我们建设的这套体系与行业里主流的 Agent Harness 不是一回事，但有紧密联系——

  • 行业主流的 Harness（如 Cursor、Claude Code 内置的）是运行时骨架层：负责 while 循环怎么写、工具怎么注册、上下文怎么管理，让 Agent 能跑起来
  • 我们建设的 Harness 是工程规范层：负责规矩怎么定、文档怎么写、测试怎么验收，让 Agent 跑得对、跑得稳

两者是上下层关系：下层是基础设施，上层是业务规则。要理解我们做了什么，需要先了解行业主流的 Agent Harness 是什么。

3.1 行业主流 Agent Harness 解决什么问题

裸用 AI 写代码的常见痛点：

痛点 具体表现
带不走状态 换个会话，规矩要重新讲一遍
不知道公司规范 AI 不知道你的分层架构、命名约定
无法验证对错 代码生成了，但怎么算对？没有验收标准

一句话定义：Agent ≈ Model + Harness

  • Model（模型）：负责理解与生成
  • Harness（套具）：负责把生成结果接在真世界和真标准上

Harness 就是把 规则文件、标准文档、运行命令、测试与验收清单 等固化进仓库和工具链，让 AI 产出可约束、可复现、可验收。

3.2 行业主流 Agent Harness 的结构

Agent Harness（运行时骨架层）
├── 循环控制器（何时停？）
│   ├── 硬性上限（max_turns）
│   ├── LLM 主动停止（stop_reason == "end_turn"）
│   └── 循环检测（工具名+参数重复？）
├── 工具管理器（怎么调？）
│   ├── 工具注册（TOOLS 描述）
│   ├── 工具路由（TOOL_MAP 映射）
│   └── 错误处理（喂回 LLM 还是硬停？）
└── 上下文管理器（记忆怎么管？）
    ├── 硬性裁剪（只保留最近 N 轮）
    ├── 摘要压缩（LLM 自己总结）
    └── 关键钉住（system-reminder 模式）

这是 Cursor、Claude Code 等 AI 编程工具已经实现的运行时基础设施——让 Agent 能跑起来。

3.3 Agent 运行循环流程

flowchart LR
  A[用户输入] --> B[LLM思考]
  B --> C{需要调工具?}
  C -->|是| D[调用工具]
  D --> E[工具返回结果]
  E --> B
  C -->|否| F[最终回答]
  F --> G[结束]

核心要点：

a. Harness 的循环次数不是人控制的，而是 LLM 根据任务复杂度自主决定 b. 错误不是终点，而是信息 — LLM 看到错误后能自己换策略 c. 上下文会越来越大，Harness 负责裁剪和记忆管理 d. 所有 Agent 框架（LangChain、CrewAI、Claude Code）本质上都是这个循环的变体

3.4 关键认知

行业共识：Agent Harness 是让 AI 在生产环境中可靠运行的基础设施层。 但这只是"运行时骨架层"——让 Agent 能跑起来。

四、我们的做法：双层 Harness 架构

4.1 双层架构图

┌─────────────────────────────────────────────────┐
│          我们建设的 Harness（工程规范层）          │
│  Policy / Procedure / Context / Tools / Eval     │
│  "规矩、文档、测试、验收怎么设计"                  │
│                                                 │
│  ┌─────────────────────────────────────────────┐│
│  │      行业主流的 Harness（运行时骨架层）       ││
│  │  循环控制器 / 工具管理器 / 上下文管理器        ││
│  │  "while 循环怎么写、工具怎么注册"             ││
│  └─────────────────────────────────────────────┘│
└─────────────────────────────────────────────────┘

4.2 为什么是上下层关系

层级 谁做的 做什么 类比
下层（运行时骨架） AI 工具厂商（Cursor、Claude Code） while 循环、工具注册、上下文管理 汽车引擎
上层（工程规范） 我们需要建设的 规矩、流程、资料、工具环境、验收 交通规则 + 驾驶手册 + 质检流程
  • 下层让 Agent 能跑起来
  • 上层让 Agent 跑得对、跑得稳

4.3 五层模型速查表

层次 一句话 像什么 与行业 Harness 的对应
规矩（Policy） 哪些必须遵守、哪些绝对禁止 交规、红线 循环控制器的"停止条件"
流程（Procedure） 文档写什么章节、类怎么分层 操作手册、模板 工具管理器的"工具描述"
资料（Context） 真相以哪份文档为准 合同与图纸 上下文管理器的"记忆管理"
工具与环境（Tools） Gradle、数据库、脚本 车间与设备 工具管理器的"工具执行"
验收（Eval） 自动测试 + 怎么算对的清单 质检与对账 循环控制器的"完成判定"

4.4 Harness 控制流图

flowchart TB
  policy["Policy 策略与规则"] --> proc["Procedure 程序与标准"]
  proc --> ctx["Context 版本化文档"]
  ctx --> tools["Tools 工具与环境"]
  tools --> eval["Evaluation 测试与验收"]
  eval -->|反馈：更新文档与规则| proc

读图要点：Eval 发现问题后，理想路径不是"再聊一轮"，而是反馈进程序层与上下文（修标准文档、补 Rule），使 Harness 加厚。

六、提效成果

6.1 效率提升（定性描述）

由于项目未保留传统模式的基线数据，以下基于团队实际感受的定性评估。

6.1.0 各职能效率提升总览

本项目 AI 辅助提效不只体现在后端开发环节，而是覆盖了业务产品、前端开发、后端开发、测试等多个职能。以下逐一按职能梳理：

6.1.1 业务产品：用 AI 做可交互原型

背景：本项目业务负责人多年前做过产品经理，但当前岗位是业务。由于公司没有足够的产品经理，该业务在本项目中兼任产品角色。

做法：使用 Google AI Studio 制作可交互原型，替代传统的 Axure/Figma 画图流程。

效率提升一：原型设计从 2 个月缩短到 2 天

对比维度 传统模式（Axure/Figma） AI 辅助模式（Google AI Studio）
产出速度 从立项到研发可开始，中间至少 2 个月 初版整体设计仅用 2 天（且是闲散优哉的状态）
评审焦点 浪费大量时间在讨论交互设计和文字描述，因每个人脑补不同而争吵 评审直接聚焦业务逻辑——"做不做"而非"怎么做"
沟通效率 每次评审-修改-再评审循环都要重新对齐视觉理解和业务理解 可交互原型所见即所得，stakeholder 无需脑补还原

关键转变：评审会议从"这个按钮放左还是放右"或“产品文字描述不正确或不全”的低价值争论，变成了"这个业务要不要做"的高价值决策。AI 原型消除了交互设计层面的无意义消耗，把团队精力集中在真正重要的事情上。

效率提升二：节省了一个产品经理的人力编制

对比维度 传统模式 AI 辅助模式
岗位需求 必须招聘专职跨境电商产品经理 业务人员用 AI 兼任产品角色即可
交付结果 无产品经理难以按期交付 一季度按期交付了完整的跨境电商后台管理系统
HR部门 项目初期为"必须招聘" 项目中后期变为"没必要招聘了"
后续 PRD 产品经理专职编写 其他产品经理用 AI 兼顾即可完成

直接成本节省：为公司节省了一个产品经理的人力编制费用。

效率提升三：可交互原型作为"项目生存战略工具"

背景：项目立项初期，业务产品和客服总监（公司股东之一，也是该后台的主要用户方）围绕 Xmind 脑图争论不休——"做什么、不做什么、某个模块做成什么样"，各方脑补不同，争论难以推进。

项目经理的决策逻辑：

传统模式风险：
Xmind 脑图 → 各方脑补不同 → 争论 2 个月 → 老板/股东看不到实物 →
项目资源不到位 → 新项目有可能半路上夭折在摇篮里

AI 原型破局：
Google AI Studio → 2 天出可交互原型 → 各方眼见为实 →
股东快速认可 → 人/财/物/时间资源到位 → 项目成功启动并有充足的支持、足够低的压力来完成交付

关键洞察：可交互原型不仅是开发工具，更是向投资人（公司老板和股东）争取资源的"创业路演工具"。

对比维度 传统模式（Xmind + 文字描述） AI 辅助模式（可交互原型）
决策周期 争论数周，各方脑补难以对齐 2 天内看到可点击的"真实系统"
资源获取 投资人（股东）看不到交付物，难以争取资源 眼见为实，快速获得人/财/物/时间投入
项目风险 新项目可能夭折在摇篮里 用"看得见的产品"锁定资源，项目成功启动
争论焦点 "你认为做成这样，他认为做成那样"的低效拉扯 对着可交互原型讨论，所见即所得

项目经理的判断：就像创业路演一样，必须让投资人立刻看到交付物并认可，才能争取到资源。2 个月的等待期对新项目来说是致命的。

前端团队编写了一套项目专属的 Rules（编码规范）和 Skills（操作步骤），然后按以下流程让 AI 生成页面代码：

  B --> C[TREA 生成<br/>UI + 交互 + 业务逻辑]
  C --> D[人工逐行审核代码]
  D --> E[反向优化<br/>Rules 和 Skills]
  E -.->|持续改进| B
维度 具体做法
输入素材 google ai studio 可交互原型截图 + Swagger 接口文档 + 项目级 Rules + 项目级 Skills

持续改进 审核中发现的问题反向优化 Rules 和 Skills，形成正循环

做法二：Bug 修复的"截图 + 定位 + Skills"模式

前后端联调和 Bug 修复阶段，前端采用标准化的 AI 辅助修 Bug 流程：

② 定位 人工初步排查，定位到具体代码文件
③ 喂入 截图 + 代码文件 + Skills 名称 → TREA
④ 修复 AI 基于 Skills 中的代码规范来修改 Bug，保持代码风格一致性

做法三：按场景选择模型

前端团队在 TREA 中根据任务类型选择不同模型：

任务类型 选择模型 原因
UI 还原 Gemini 还原页面视觉效果更好
业务逻辑 GPT-4 逻辑推理和代码组织更强

做法四：Google AI Studio 辅助理解业务

前端开发过程中，使用 Google AI Studio 来帮助理解业务需求，降低了对业务背景知识的依赖门槛。

效率提升总结：

维度 传统模式 AI 辅助模式 提升感知
页面开发速度 逐页手写，单个页面数小时 截图 + AI 生成，约 15 分钟/页 产出速度数倍提升
代码规范一致性 依赖人工记忆和 Code Review Rules + Skills 自动约束生成规范 风格一致性显著提高

维度 传统模式 AI 辅助模式 提升感知
文档产出 手动编写，每个文档需数小时 AI 按模板生成初稿，人审核修改 产出速度显著提升
代码生成 逐行手写，包括样板代码 AI 生成基础结构，人聚焦业务逻辑 重复性编码工作大幅减少
测试编写 手动编写测试用例 AI 生成测试骨架和断言 测试覆盖率更易达标
新成员上手 口头讲解 + 翻找零散文档 打开仓库即可看到完整的规范体系 学习曲线明显缩短
换人/换模型 重新口述规范 规范已在仓库中，自动加载 知识不随人员流失

6.1.4 测试：AI 提效不明显及改进方向

现状：AI 对测试环节提效不明显

测试团队反馈，当前 AI 辅助对测试工作的效率提升有限，主要受限于两个因素：

问题一：缺乏文字版 PRD，测试用例生成困难

现状 影响
没有文字版 PRD 测试无法直接通过 AI 生成完整测试用例
依赖可交互原型"点点点" 测试人员需手动在 Google AI Studio 原型上扒业务逻辑和细节，效率低
后端提供的测试用例不全 即便有部分测试用例，覆盖度仍不足以支撑完整测试

问题二：后端改 Bug 引入回归问题，测试反复验证

现象 原因分析
"摁下葫芦又起瓢" 后端用 AI 改 Bug 时生成新 Bug，甚至已修复的 Bug 重新出现
AI 生成代码过多 后端无法逐行审核所有 AI 生成代码，直接提交测试
缺乏回归防护 没有前置的自动化端到端测试拦截回归问题、保证AI不改坏业务逻辑

改进方案：接口文档前置 + 自动化测试左移

测试团队提出的 Harness 层改进建议：

flowchart LR
  A[后端开发前<br/>输出 Swagger 接口文档] --> B[测试基于接口文档<br/>编写自动化测试脚本]
  B --> C[后端开发/改 Bug 后<br/>先跑自动化脚本自测]
  C -->|通过| D[提交测试]
  C -->|不通过| E[继续修复]
  E -.-> C
改进措施 对应 Harness 层 预期效果
后端优先提供 Swagger 接口文档 Context（资料） 测试有明确的契约依据
测试提供接口自动化测试脚本 Tools（工具） 可重复运行的回归验证手段
后端提测前强制自测通过 Eval（验收） 拦截"摁下葫芦又起瓢"问题

Insight：测试团队反馈的"摁下葫芦又起瓢"现象，暴露了 Harness 架构中 Policy（规矩）层 和 Eval（验收）层 的缺口——没有硬性约束 AI 生成代码的审核深度，也缺乏端到端自动化测试作为回归防护。测试提出的"接口文档前置 + 自动化测试左移"方案，正是补全 Tools + Eval 层的典型思路。

6.1.5 新后端接手：换人场景下的 AI 辅助体验

背景：研发提测后两周，新加入一名后端开发接手项目，项目仍保持后端一人配置。

观察一：可交互原型加速业务上手

对比维度 传统模式（Axure + 文字 PRD） AI 辅助模式（Google AI Studio 可交互原型）
业务理解速度 需多次沟通、反复确认业务逻辑 业务产品只需讲解一次，通过可交互原型快速理解业务全貌
信息对齐 Stakeholder 各自脑补，理解容易偏差 所见即所得，各方对业务的理解一致性显著提高
新人上手 测试和客服总监新加入项目时也面临同样困境（文档散落在各处） 可交互原型成为统一的事实来源，测试、后端和客服总监都能快速跟进业务

关键发现：可交互原型不仅服务于前端开发，更是跨角色业务对齐的最佳媒介——比文字 PRD 更直观，比静态原型更真实。

观察二：AI 生成代码的质量债务

新后端接手后发现的代码质量问题：

问题现象 具体案例 根因分析
代码量过多 部分功能 AI 生成了大量冗余代码 缺乏对生成代码规模的硬性约束
实现不严谨 多处存在循环中调接口的性能隐患 AI 追求功能正确，忽视性能和质量细节
隐性技术债务 代码能跑，但存在可优化空间 前期追求速度，未做深度 Code Review

观察三：改 Bug 的工作模式

新后端改 Bug 的方式与前端类似：

人工初排定位 → 截图 + 文件 → 喂给 AI → AI 修改

差异点：新后端没有特别提到其有使用项目级 Skills，可能是接手时未继承到或了解到这部分资产。

换人场景的 Harness 启示：

flowchart TB
  subgraph good [理想状态：Harness 完善]
    A1[可交互原型] --> B1[新成员快速理解业务]
    C1[共享 Rules/Skills] --> D1[代码风格一致性]
    E1[自动化端到端测试] --> F1[改 Bug 不引入回归]
  end

  subgraph actual [本项目：Harness 待完善]
    A2[可交互原型] --> B2[业务上手快 ✓]
    C2[使用 Rules/Skills 的经验未共享] --> D2[代码质量波动 ✗]
    E2[缺少自动化端到端测试] --> F2[改 Bug 易回归 ✗]
  end
Harness 层 现状评估 改进方向
Context（资料） 部分缺失 项目级 Skills 需文档化、共享化
Policy（规矩） 待补强 增加代码生成规模和审核深度的硬性约束
Eval（验收） 待建立 接口自动化测试作为改 Bug 的前置门禁

Harness Engineering 视角：对抗 AI 代码生成的"熵增"

新后端接手的体验揭示了 Harness Engineering 的核心命题——AI 代码生成天然带有"熵增"属性：

AI 生成代码的熵增定律
├── 规模熵增：单次生成代码量不受控，越积越多
├── 质量熵增：追求功能正确，忽视性能/可维护性
└── 知识熵增：个人经验沉淀为 Skills，但未共享即流失
熵增类型 本项目表现 Harness 层的熵减策略
规模熵增 AI 生成代码过多，人工无法逐行审核 Policy：硬性约束单次生成代码行数上限
质量熵增 循环中调接口、代码冗余等隐性债务 Eval：自动化测试 + Code Review 强制门禁
知识熵增 Skills 文件已传递，但如何使用好这些 Skills 未完全传递给新后端 Context：Skills 使用经验需文档化、案例化、可复现

Harness Engineering 的本质：不是阻止 AI 生成代码，而是建立持续的熵减机制——把个人经验转化为团队规范，把隐性债务转化为显性约束，把一次性正确转化为可持续正确。

Insight："熵增熵减"框架的引入为 Harness Engineering 提供了理论深度：

  • 规模熵增 → Policy 层的硬性约束（如单次生成代码行数上限）
  • 质量熵增 → Eval 层的自动化验收（如测试门禁、Code Review）
  • 知识熵增 → Context 层的文档化共享（如 Skills 版本化）

这与热力学第二定律形成有趣类比：AI 代码生成如同一个开放系统，如果不持续做功（Harness 约束），必然趋向混乱。Harness Engineering 就是对这个系统持续"做功"的工程方法。

6.2 关键成果：可复用的工程规范资产

项目最大的成果不是"这一个项目做得快"，而是沉淀了一套可复用的体系：

可复用资产清单
├── 编码规范规则（自动触发，不需要人每次提醒）
│   ├── Java 代码生成规范
│   ├── 分层架构强制约束
│   └── 测试用例编写标准
├── 标准文档模板
│   ├── PRD 编写模板 
│   ├── 技术方案模板
│   └── 项目结构规范
├── 可运行的验证体系
│   ├── 单元测试命令（一键执行）
│   ├── 业务验收方案（公式 + SQL + 场景）
│   └── 问题根因与规避标准
└── 工作流 Skills（可引用的做事步骤）
    ├── 代码生成步骤
    ├── 测试编写步骤
    └── 变更管理流程

与 Harness 五层的对应关系：

资产类型 对应 Harness 层
编码规范规则 Policy（规矩）
标准文档模板 Procedure（流程）
可运行的验证体系 Tools + Eval（工具与验收）
工作流 Skills Procedure（流程）

这套资产的核心价值：新项目、新同事、甚至换了 AI 工具，规范体系不受影响。

6.3 业务设计质量

AI 辅助不只是"写得快"，在规范约束下，产出质量也有保障：

设计决策 说明
统一单据驱动 所有库存变动都经过"统一入库单/出库单"抽象层，新增业务类型只需扩展映射，不改核心逻辑
可替换策略 金额口径、分摊规则等高频变更点设计为可替换策略，避免一改全崩
闭环验证文档 订单同步到库存扣减全链路有书面验收方案，每次迭代可重复验证

七、质量保障：三层把关体系

通俗解释：不是 AI 写完就算了，而是有三层检查机制确保质量。

┌─────────────────────────────────────────────────────┐
│                第一层：机器自动检查                      │
│   编译通过 + 单元测试全绿                               │
│   捕获：语法错误、逻辑回归、接口契约问题                    │
├─────────────────────────────────────────────────────┤
│                第二层：数据关系断言                       │
│   库存数量恒等式、字段约束等写入测试                      │
│   捕获："每段代码单独正确，拼起来违反约束"的静默错误        │
├─────────────────────────────────────────────────────┤
│                第三层：业务验收方案                       │
│   按场景、按公式、按数据库表核对                          │
│   捕获：跨表业务口径错误、金额尾差等业务层面问题            │
└─────────────────────────────────────────────────────┘

关键认知：只有第一层容易给人"全绿即正确"的错觉；真正保障业务正确性的是第二层和第三层。这三层对应 Harness 的 Eval（验收）层。

八、踩过的坑：真实问题与解决

展示三个真实案例，说明我们如何把问题转化为可复用的规范。

坑 1：汇总数和明细数对不上

项目 说明
现象 页面上显示的库存总数，和逐行明细加总不一致
根因 汇总和明细走的是不同的数据聚合路径，没有提前规定"以谁为准"
解决 在标准文档中写明"多数据源展示必须声明一致化策略"，并增加自动化断言
教训 不是"AI 写错了"，而是规范里没规定清楚
Harness 层面对应 Context（资料）层缺口 + Eval（验收）层缺失

坑 2：库存恒等式没写进测试

项目 说明
现象 改了代码后测试还绿，但实际已违反了数量关系
根因 库存数量关系（总量 = 可卖 + 已占）只在方案文档里，没写进查询和测试
解决 把恒等式写入 SQL 注释和单元测试断言
教训 写在文档里的规则，必须也能被机器自动检查
Harness 层面对应 Eval（验收）层缺口

坑 3：验收结果时好时坏

项目 说明
现象 同一个验收脚本，有时通过有时不通过
根因 代码已修复但服务没重启，验收跑在旧代码上
解决 在验收文档中明确"代码变更后必须重启服务才能验收"
教训 环境状态也是质量体系的一部分
Harness 层面对应 Tools（工具与环境）层缺口

这三个坑的共同规律：每次出问题后，我们都把教训写进了规范——不是反复叮嘱 AI，而是让规范自动生效。

九、与其他团队的可推广性

9.1 最小可复用"四件套"

其他团队要复用这套方法论，最少需要四样东西：

序号 资产 说明 像什么 对应 Harness 层
① 自动触发的规则 编辑代码时自动加载编码规范 交规 Policy
② 一份标准文档 规则引用的主标准，而非散落在对话里 操作手册 Procedure
③ 一条测试命令 所有人跑同一条命令验证质量 质检流程 Eval
④ 核心链路验收方案 公式 + 场景 + 数据库核对 对账单 Eval

9.2 人必须拍板的事

AI 不能替代人的决策：

  • 需求取舍（做什么、不做什么）
  • 线上发布与回滚
  • 跨团队协作的 SLA
  • 安全与合规审查

十、当前不足与改进方向

务实说明：体系建设已有基础，但仍有明确的短板需要补齐。

短板 现状 改进方向 Harness 层面对应
测试自动化 单元测试有规范，但集成测试、接口自动化未成体系 建立 CI 流水线，合并前必须跑通测试 Tools + Eval
持续集成 目前没有自动化的 CI 配置，合并门禁靠人工 引入 GitHub Actions 或 Jenkins Tools
规范工程化 Skills 以单文件为主，触发时机和踩坑经验不够系统 演进为目录形态，加入踩坑记录 Procedure
设计链路 设计稿和 AI 工具链未打通 探索 Figma MCP 等设计-AI 协作工具 Context + Tools
量化度量 缺乏系统性的效率数据 建立度量基线，追踪改进趋势 Eval

核心结论

  1. AI 全流程参与开发是可行的——本项目证明了从需求到验收的每个环节都可以由 AI 深度参与
  2. 效率提升的关键不只是 AI 本身——更重要的是配套的双层 Harness 架构：下层让 Agent 能跑，上层让 Agent 跑得对
  3. 最大的复利效应是可复用的规范资产——这套体系可以复用到其他项目，换工具也不受影响
  4. 仍有明确的改进空间——测试自动化、持续集成、设计链路 AI 化是下一步重点
